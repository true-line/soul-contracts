# Control records v1

These draft records implement the [accepted PDR-0047](https://github.com/true-line/agent-bot-platform/blob/main/docs/04-decisions/PDR-0047-harbor-is-the-control-plane-of-a-linked-machine.md) point 12 contract seam. Schemas check encoding and required fields. They do not make a record authoritative. A receiver must run the checks below before acting; a parser success, an owner session, and a relay do not grant authority. The qualification policy in this directory has its own signing purpose and trust roots; it is not a Harbor control key.

## Record and signature bytes

Parse strict UTF-8 JSON with duplicate keys rejected. Canonicalize with RFC 8785 JCS. For every record, `payload_sha256` (or `action_sha256`) is `sha256:` followed by the lowercase SHA-256 of the exact JCS bytes of `payload`. Compare in constant time after strict decoding. Every signature must cover the domain-separated bytes below, including the `contract` and `kind` so that a signature cannot be moved to another record family:

- Harbor control signature: UTF-8 `agent-bot/control-record/v1` + NUL + JCS of `{contract,kind,payload}`. Use the pinned Ed25519 control public key named by `control_key_id`. The key is separate from catalog and credential keys and is not supplied by the record.
- Owner device presence: UTF-8 `agent-bot/control-owner-presence/v1` + NUL + JCS of `{contract,kind,payload,owner_device_key_id,owner_session_id,challenge_nonce,expires_at}`. Verify ES256 with the enrolled P-256 device key named by `owner_device_key_id`; require the signed action hash to match `payload`. The owner device key must have been enrolled and remain unrevoked. A presence signature is for one exact action and one live local challenge, not a reusable session token.
- HQ challenge signature: UTF-8 `agent-bot/control-hq-challenge/v1` + NUL + JCS of `{contract,kind,payload}` using HQ's locally paired ES256 key. It authenticates a challenge, not an approval.
- Enrollment and local issuer signatures: UTF-8 `agent-bot/control-issuer/v1` + NUL + JCS of `{contract,kind,payload}` using a separately trusted issuer key. The issuer kind and key ID must match the local machine's trusted issuer set or the linked identity service's trusted issuer set. A record's embedded key ID never creates trust.

Base64url values are unpadded. ES256 signatures use standard base64 of DER ECDSA signatures for owner presence and HQ challenges. The issuer signature field uses unpadded base64url; its algorithm determines Ed25519 raw bytes or ES256 DER bytes. Decode strictly, reject noncanonical encodings, reject unknown algorithms, and verify signatures before consulting the record. The fixture signatures are synthetic shape examples; a runtime must not accept them as proof.

## Enforcement

First-device enrollment is a narrowly scoped local-only bootstrap: it is allowed only when no owner device is enrolled, while the owner is physically authenticated at the machine. Machine/keyd runs in the secure administrative account and issues a fresh local challenge, confirms the owner-presence prompt, checks the local owner account and UID, verifies the proposed device key signs `agent-bot/control-first-device-possession/v1` + NUL + JCS of `{contract,kind,payload}`, then signs `agent-bot/control-first-device-presence/v1` + NUL + JCS of `{contract,kind,payload,local_owner_account,local_owner_uid,machine_challenge_nonce,device_possession_signature_base64}` with its locally pinned Ed25519 presence key. HQ verifies that key, challenge, account, UID, proof and the separate local issuer signature before storing the device. A Harbor key or account cannot bootstrap enrollment. All additional devices require fresh presence from an already enrolled, unrevoked owner device; first-device mode is refused once any owner device has been enrolled.

The owner physically links or unlinks at the machine. A link pins the exact Harbor control public key under owner presence. Rotation requires a record signed by the currently pinned key with `previous_control_signature.payload_sha256` bound to the exact rotation payload *and* new owner presence; revocation at the machine or with owner presence immediately refuses the revoked key. No key may be replaced through a policy bundle or a relayed request. Link IDs, machine IDs, sessions, policy revisions and hashes must match local durable state. Replay of a consumed nonce, session exchange, link transition or request ID is refused, including after restart. HQ and Machine each verify owner presence for every widening act, regardless of transport.

A policy bundle is an ordered, signed snapshot. `policy_revision` must be strictly greater than the greatest durable accepted revision, and `previous_policy_sha256` must bind the previous accepted bundle (null only for the first bundle after physical link). A claimed `reduce` must be a subset of prior allowed actions; any new permission is `widen` and needs presence. The issuer's `allowed_actions` is a closed set of exact `{verb,resource}` pairs, never a pattern. The relayed request carries unpadded base64url of strict JCS parameter bytes; verify its `parameters_sha256` before passing those bytes to an operation. An operate request must match a pair in the current signed policy, its pinned key, exact link and machine, and unexpired owner link grant. A reduce request cannot conceal an operate or widen verb. `authority_class` and `operation` must agree; reject inconsistent pairs. A widening request needs fresh owner presence and still must obey the local host constraints.

A signed bundle expires at `expires_at`. While the link is live, no expired bundle authorizes operate or widen. On link loss, HQ retains the last verified bundle as a restrictive ceiling, accepts only reduce actions, and never treats expiry as a reason to fall back to a wider local policy. Already admitted work that needs no new credential may continue under its existing grant. On unlink, local-only authority resumes with its own local policy and credentials; Harbor reachability, Harbor accounts and Harbor keys are not prerequisites for local-only operation or conformance.

Open/exchange binds a local HQ challenge and machine ID to an owner session. In linked mode the exchange requires enrolled device presence; in local-only mode the local peer account and UID are checked on the local socket. A session is only authentication. Linked machine plans additionally require the pinned Harbor control signature; local-only machine plans forbid it and any link ID. Machine plans require owner presence over the exact canonical plan bytes and digest; decoded plan machine and operation must match the record. Local credential issuance uses a distinct `records/v1` variant with `issuer_kind: local-machine`; it does not claim an identity service signature. Every credential issuance still binds owner, device, Soul, grant, scope, audience, expiry and DPoP thumbprint. No record carries credential material.

Reject unknown fields, stale times, malformed or mismatched binding, wrong or revoked key, missing owner presence, disallowed action, replay, and contradictory classification. Return a registered refusal that matches the cause: `owner_presence_missing`, `control_key_revoked`, `control_key_unrecognized`, `issuer_untrusted`, `control_binding_mismatch`, or `action_outside_policy`. The schema and fixture validator checks structural and deterministic binding cases; production implementations must independently verify cryptography, state transitions and clock rules.
