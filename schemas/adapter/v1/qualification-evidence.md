# Draft qualification evidence payload

The [draft attestation contract](qualification-attestation.md) binds this record when it is delivered as the exact `qualification.json` file.

This is a proposed payload shape for [qualification tracking](https://github.com/true-line/soul-contracts/issues/45), not a signed record or an authorization. Its example is synthetic. A valid payload can describe a failed or incomplete run and does not establish that any adapter is qualified. The existing manifest schema continues to accept only an empty `profiles_qualified` list.

The payload records one exact adapter package, executable path and file digest, ordered fixed argument vector (excluding the executable), all additional fixed code inputs and their digests, absolute harness binary path and digest, named host and profile actually in force. For an interpreter, code inputs include the script and loaded modules; an empty list asserts that there are none. It records the independent conformance suite revision, run and report, evaluation cells naming role, revision, harness context, model and provider, dated observations and content-digested references for host and each check. The observations cover the adapter qualification guidance: egress, credentials, native state redirection, interruption and resume, session reuse, cost bounds and rendering. Their outcomes may include failure, unenforced and not-run. The attestation contract defines how the physical macOS reports identify the gates and their profiles under the owner decision. Shape alone cannot decide whether any particular report passes those requirements. See the [qualification guide](https://github.com/true-line/agent-bot-platform/blob/main/docs/user-guide/adapters/adapter-qualification.md) and [traceability matrix](https://github.com/true-line/agent-bot-platform/blob/main/docs/02-requirements/traceability-matrix.md).

Machine verifies that the fixed launch selects the recorded harness path and digest. The installation can contain two working harness versions. If the adapter selects the other one at startup, the verifier must refuse the qualification even when the recorded file is present and its hash matches. An unresolved choice must also fail verification. The payload shape alone cannot demonstrate how an adapter selects a child process.

The hashes and references are claims until independently checked. The attestation contract describes what Machine must verify before a record can authorize a protected profile. An owner-reviewed local installation remains a separate requirement. The fixed code-input list requires independent verification of which files are actually loaded. The evidence schema continues to describe unqualified and cooperative observations, including records without a designated host ID.
