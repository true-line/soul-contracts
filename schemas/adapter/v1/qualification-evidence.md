# Draft qualification evidence payload

This is a proposed payload shape for [qualification tracking](https://github.com/true-line/soul-contracts/issues/45), not a signed record or an authorization. Its example is synthetic. A valid payload can describe a failed or incomplete run and does not establish that any adapter is qualified. The existing manifest schema continues to accept only an empty `profiles_qualified` list.

The payload records one exact adapter package, executable path and file digest, ordered fixed argument vector (excluding the executable), all additional fixed code inputs and their digests, harness binary digest, named host and profile actually in force. For an interpreter, code inputs include the script and loaded modules; an empty list asserts that there are none. It records the independent conformance suite revision, run and report, evaluation cells naming role, revision, harness context, model and provider, dated observations and content-digested references for host and each check. The observations cover the adapter qualification guidance: egress, credentials, native state redirection, interruption and resume, session reuse, cost bounds and rendering. Their outcomes may include failure, unenforced and not-run. For protected evidence, the hostile-member suite includes T01, T02, T03 and T21; a cooperative run must report the profile in force. Shape alone cannot decide whether any particular report passes those requirements. See the [qualification guide](https://github.com/true-line/agent-bot-platform/blob/main/docs/user-guide/adapters/adapter-qualification.md) and [traceability matrix](https://github.com/true-line/agent-bot-platform/blob/main/docs/02-requirements/traceability-matrix.md).

The hashes and references are claims until independently checked. Before a record can authorize a profile, the platform must decide the signing authority, trust chain, signed envelope and canonical bytes, key lifecycle and revocation, offline verification and failure behavior. Machine and HQ must independently verify signature and trust, revocation, report provenance and digest, suite revision and test outcomes, and match the exact installed adapter package, executable path and bytes, ordered arguments, complete code-input set and bytes, harness binary, host and profile against the verified record. Completeness of dynamically loaded code also needs an enforceable resolution and verification rule; a list by itself does not prove it. They must refuse missing, changed, unknown or revoked qualifications. An owner-reviewed installation remains a separate requirement. Cross-consumer fixtures must test changed executable, arguments and code inputs, unqualified and revoked records, and identical decisions; those are verification tests, not JSON shape errors. Date and references do not themselves prove freshness or integrity. Until that work is specified and implemented, this draft must not be used to enable a nonempty qualification list or a protected launch.
