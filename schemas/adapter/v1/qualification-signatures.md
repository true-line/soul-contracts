# Authenticated macOS qualification evidence

This draft specifies the byte and signature boundary for [PDR-0102](https://github.com/true-line/agent-bot-platform/blob/main/docs/04-decisions/PDR-0102-protected-adapter-qualification.md). It adds no qualified manifest entry. A report is evidence only after the designated host's independently observed run is complete; a valid JSON shape or signature over a self-reported result alone is insufficient.

## Fixed host report signature

The exact signing purpose is ASCII `agent-bot/qualification-host-report/v1`. The report is a UTF-8 RFC 8785 JSON Canonicalization Scheme document without BOM or terminal newline. Parse it with duplicate-key rejection; canonicalizing the parsed value must reproduce the same bytes. The ES256 signing preimage is `ASCII(purpose) || 0x00 || report_bytes`. ES256 uses SHA-256 and a P-256 Secure Enclave key; `signature_base64url` carries the 64-byte `r || s` signature in unpadded base64url. The [host signature envelope](qualification-host-signature.schema.json) carries the report bytes, their SHA-256, `host_id`, `signer_id`, purpose and signature. Base64url decoding must be strict, canonical, and size bounded. The envelope's host ID must equal `report.host.id`; its signer ID and public P-256 SPKI key must match the one owner-policy `evidence_signers` entry designated for that host. Ordinary device enrollment is not designation. keyd may use a device-bound key only after the owner explicitly designates its public key for this fixed purpose.

The first Machine/keyd verifier accepts only the ASCII subset of JCS and refuses a canonical report or policy containing non-ASCII bytes. This is a narrower supported input set, not an alternate canonicalization or a reason to trust reserialized bytes.

Machine constructs the keyd request after an owner-approved, one-use run has been consumed and a separate immutable completed-run record has been written. The completed record binds the exact approved plan and candidate digest, report digest, runner digest, host ID, observed HQ-started Soul process and physical results. Machine must independently observe the HQ process and the `agent-bot-souls run` child executable, UIDs, argv digest and active profile while they are live. `soul_start.hq_launch_receipt` is supporting evidence; `soul_start.machine_observation` identifies Machine's observation. Neither a receipt hash claimed by HQ nor a `started` or failed attempt record establishes this observation. keyd checks the fixed report shape and Machine-signed request, and does not offer general signing. No completed-run producer currently exists, so this operation must remain unavailable to ordinary callers.

## Owner policy and release trust

The [owner policy envelope](../../control/v1/qualification-policy-envelope.schema.json) contains the exact JCS bytes of the decoded [control/v1 qualification trust policy](../../control/v1/qualification-trust-policy.schema.json) and an Ed25519 signature over `ASCII("agent-bot/qualification-policy/v1") || 0x00 || policy_bytes`. Its `owner_key_id` selects only a public owner root compiled into and reviewed with the Machine release; an envelope cannot supply or replace its own root. Machine ships an initial signed policy, persists the greatest accepted revision across restarts, and accepts a later revision only after verifying its owner signature and time bounds. HQ is a transport for updates, with no signing authority. The policy pins the designated host IDs and SPKI keys, one release workflow ID, repository, exact source commit, workflow path, OIDC issuer, certificate identity and trust-root digest, and the complete revocation snapshot.

The release artifact is a Sigstore bundle v0.3 JSON document with media type `application/vnd.dev.sigstore.bundle.v0.3+json`. It carries exactly one DSSE signature over an in-toto Statement v1 payload with payload type `application/vnd.in-toto+json`, the fixed qualification predicate type, and exactly one `qualification.json` SHA-256 subject digest. Its `predicate.release` source repository, commit and workflow path must agree with owner policy. The bundle has exactly one Rekor transparency-log entry with a verified inclusion proof and signed checkpoint, plus at least one independently verified observer timestamp from a signed entry timestamp or RFC 3161 authority. The Fulcio leaf certificate needs a verified certificate-transparency timestamp. Machine authenticates the certificate chain and timestamps using only the exact local trusted-root JSON bytes whose SHA-256 the owner policy pins. It requires the exact pinned OIDC issuer, certificate identity, source repository URI and source commit in the authenticated certificate. No TUF, Rekor, certificate or policy network lookup is permitted during verification.

The bundle is at most 4 MiB, the local trusted-root document at most 1 MiB, and the signed statement and `qualification.json` each at most 1 MiB. Machine hashes the exact delivered bundle bytes against the installed manifest's qualification reference and rejects a revoked digest. It verifies the subject against the exact delivered `qualification.json` bytes, then verifies every referenced canonical host-report byte sequence and designated-host signature. A build-provenance predicate or unsigned statement is insufficient. An actual owner-pinned root, initial signed policy, release-produced bundle and physical reports remain required before a production launch can accept a positive qualification.

## Offline verification order

Machine verifies the pinned owner root and policy signature first; rejects rollback, policy expiry, a future revocation snapshot, and `now - revocation_snapshot.updated_at > 3600` seconds. Exactly 3,600 seconds is current. It rejects revoked workflow IDs, host signer IDs and attestation digests. It then authenticates the release bundle and each exact host-report byte sequence and designated host signature. It compares the reports with `qualification.json`, then independently measures released package bytes, executable and ordered arguments, complete code-input set, selected harness, runner, host facts, profile and HQ-started Soul observation. T01/T02/T03 must pass under protected enforcement and T21 under cooperative enforcement on the physical designated Mac. A valid signature cannot promote a VM or synthetic run to physical evidence. Machine pairing and the separate exact local launch-rule approval must still be live. Any missing, unknown, changed, stale, unverifiable or revoked input refuses protected launch and Stage 2a acceptance.
