# Draft qualification attestation contract

The [owner decision](https://github.com/true-line/agent-bot-platform/discussions/102#discussioncomment-19798348) defines the qualification authority and offline policy. This draft specifies the record and cross-record checks for a protected qualification on the designated macOS host. The cooperative T21 report is one input to that protected decision. The contract defines no cooperative or non-macOS qualification.

A release qualification uses a signed [in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md) with predicate type `https://true-line.ai/soul-contracts/adapter/v1/macos-protected-qualification`. The statement has one subject named `qualification.json`. The verifier calculates `subject[0].digest.sha256` from the exact bytes delivered as that file before decoding it. JSON reserialization, including adding or removing a final line break, changes the subject digest. A build-provenance statement fails the qualification predicate check even when it names the same subject and digest. The statement schema checks the payload of an externally verified signed bundle. The signed predicate requires an explicit RFC 3339 `expires_at` later than the record and host report dates. A qualification is expired at that instant. A record or host report dated after verification time is refused. Qualification expiry has no default lifetime and is separate from trust-policy freshness.

A future `profiles_qualified` entry uses the draft qualification reference shape. It names `managed-protected` and refers to the signed attestation bundle by its SHA-256 byte digest. The verifier matches the profile to the qualification and the profile actually in force. The existing unqualified manifest still requires `profiles_qualified: []`. This draft does not introduce a qualified manifest format or enable production launches.

The qualification statement references fixed conformance report payloads by their exact byte digests. The release workflow and Machine verify the signed host report payloads against the designated evidence signer identities in owner policy. Every report must name the same stable `host.id`, OS, OS version and architecture as the qualification. The authenticated signer for each report must be designated for that host ID by owner-controlled policy. In a report, `profile_in_force` describes the enforcement observed during that run. Evidence from generic enrollment, a build-provenance bundle or an unsigned run cannot satisfy these checks. The same exact adapter and selected harness inputs and suite revision must be evidenced across the reports. Each gate carries a result and evidence digest, and the physical macOS release evidence must cover T01, T02 and T03 under `managed-protected` and T21 under `managed-cooperative`.

The record's `conformance.report` must identify one verified report by digest. Its run ID, host, profile, evaluation cells, render classes, cost-bound classification and reported checks must agree with that report. The qualification and reports must describe passing runs, and the required gates must all pass. In a protected report every required check must pass, including egress, credentials, native-state redirection, safe interruption and resume, session reuse, cost bounds, and render coverage. A passing check can verify an accurate capability declaration such as `cost_bound: "none"`. Cooperative T21 evidence can report applicable checks as unenforced. Machine compares the independently measured installed package, executable path and digest, ordered arguments, complete code-input set by path and digest, selected harness path and digest, host facts and active profile with the record. A digest of a report is no substitute for its verified bytes and a declared harness path does not establish which harness the adapter selects.

Each record and report also binds the exact independent runner binary and an HQ-started Soul receipt plus Machine's separate process observation. The protected release statement names the exact release source commit and workflow path. The [signature contract](qualification-signatures.md) fixes the bytes, purpose and offline trust checks. The fixture suite supplies synthetic report, software and installed-input data. The separate soul-adapters test-only workflow produced signed bytes in `fixtures/qualification/macos/release-produced-test-only/` using disposable owner and host keys. Those signatures establish no production trusted issuer or physical host evidence. HQ can deliver a newer owner-signed trust and revocation policy. Machine verifies that policy offline, enforces its validity period, rejects rollback and limits revocation snapshot age to 3,600 seconds. Production positive qualification remains unavailable until owner roots, release and host signatures, process observation, installed measurements, pairing and physical results are verified.

Run `python scripts/validate.py` with the repository's validation dependencies. The exact qualification, observed inputs and report payloads for the byte-binding fixture are in `fixtures/qualification/macos/`.
