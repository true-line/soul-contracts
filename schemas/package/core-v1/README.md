# Portable package core inspection records

`package/core-v1` is a draft schema family with its own version. The contract field selects record semantics. The layout selects path roles. The revision profile selects the procedure for identifying covered bytes. A reader needs all applicable identifiers. The paper revision, schema release, harness version and host software version have independent lifetimes. [Native Shareable Soul Packages, Draft 0.3, §§2–3, 7, 14–16 and Appendix C](https://zenodo.org/records/23547566)

| Record | Binding and scope |
| --- | --- |
| [Definition](portable-definition.schema.json) | Covered declarations for `SoulInfo.json` describe the layout, founding orchestrator, subsequently adopted harnesses and named execution profiles. Acceptance selects the revision derived from the covered definition, including instructions and the lock. |
| [Instance identity](portable-identity.schema.json) | `SoulIdentity.json` binds one stable Soul ID to an external key reference, identity-event references and a revision under a named digest profile. Authenticate this statement separately under recipient trust policy. A fork or template instantiation gets a new ID. Rotation or recovery retains the ID only with authorized continuity evidence. |
| [Acceptance](portable-acceptance.schema.json) | The authority's statement binds the exact candidate revision, expected base (null for initial acceptance), policy revision and evidence. A verifier checks authority independently of the candidate. Identical bytes may acquire another acceptance statement. |
| [Selected life checkpoint](portable-checkpoint.schema.json) | The checkpoint binds a Soul and definition to one explicit inventory of retained life at a consistency boundary. The source installation scopes its restriction epoch. An empty selection is valid. A recipient retains any known newer local restriction. |
| [Installation](portable-installation.schema.json) | A host associates a placement ID with a Soul, revision and optional selected checkpoint. The destination creates its own placement. Credentials, grants, live processes and host-local restrictions stay under host control. |

The founding orchestrator identifies the original harness and version. Adding a harness preserves this provenance. Each execution profile selects the founding harness or one of the adopted harnesses by exact ID and version, then identifies its adapter and provider independently by ID and version. The provider version describes the declared service or interface. The model is a separate selection. Runtime references resolve through the covered lock. A declared profile requests capabilities. Execution also requires a compatible local placement and current grants. [Populated definition fixture](../../../fixtures/positive/portable-definition.adopted-harness.json)

## Inspection and coverage

Paths in core-v1 inventories are relative to `Contents/`. Components use ASCII letters, digits, underscores, hyphens and periods. A leading period is valid in a filename such as `.profile`. Compare paths as ASCII bytes. Reject duplicate paths, case-fold collisions, file/directory conflicts, absolute paths, backslashes, empty and dot components. This profile inventories regular files and rejects symbolic and hard-link entries. Portable file modes are four-character octal strings. Use `0644` for ordinary files and `0755` only for executables declared by trusted policy. Preserve the logical mode independently of local filesystem permissions.

Determine coverage from the currently trusted profile and expected base. Include all behavior-bearing inputs, directly or through immutable digests in covered declarations. Classification rules and exclusion policy are themselves control-plane inputs. Reject candidate attempts to widen exclusions. An unknown executable cannot acquire an exemption through its name, directory, extension or a new candidate rule. The inventory lists the covered files. Keep the inventory's own encoding, instance identity and events, acceptance and signature envelopes, selected life and host placement outside the reusable definition bytes. Check excluded records under their own binding and trust rules.

Parse manifest JSON strictly before interpretation, including duplicate-key rejection at every nesting level. The `extensions` object in the definition holds named payloads with a required flag. Preserve unknown fields and opaque entries on a same-artifact rewrite, including unsupported records retained as opaque bytes. Unknown extensions confer no execution or export permission. A reader can inspect the supported core with an unknown required extension, but execution stays unavailable until the extension is supported. Export requires explicit selection.

After schema validation, check each execution profile against the registered harness ID and version. Check the combined definition and selected-life inventories as one path tree. Each file occurs once. Each shared directory prefix has one spelling and serves only as a directory. The record vectors replace the listed top-level fields of a positive fixture’s input. A null expected refusal means the record passes these checks. [Cross-field record vectors](../../../fixtures/package/core-v1/record-vectors.json)

## Digest and authentication profiles

`soul-core-example-1` names only the paper's three-file example. It has a fixed ASCII domain and inventory encoding. Its original `SoulInfo.json` predates the proposed core-v1 declaration fields. The two illustrative core-v1 identity statements reference those exact historical bytes. Adding founding or execution declarations to the example manifest would change its revision. [Appendix C vectors and byte recipe](../../../fixtures/package/appendix-c/README.md)

Production inventory canonicalization and hash domain, signature algorithms, key encoding, signed-envelope syntax, trust bootstrap, rotation and recovery proofs, archive and encryption profiles remain open. A schema-valid identity or acceptance statement supplies fields for authentication. Trust requires independent verification using an adopted profile and trusted keys. The separate contents-1 digest proposal has its own byte rules. [Contents-1 digest discussion](https://github.com/true-line/soul-contracts/pull/47)
