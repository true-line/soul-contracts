# Protected content for portable packages

`package/protected-v1` is a draft contract for a standalone host that inspects or restores protected Soul content. It uses the merged [core-v1 identity and checkpoint](../core-v1/README.md). Appendix C instance A retains its unsigned identity statement and definition revision. The protected fixture creates a subsequent checkpoint for four selected life files. The original Appendix C files, checkpoint and inventory remain the byte reference. [Worked vectors](../../../fixtures/package/protected-v1/README.md)

## What travels

| Record | Contents and verification |
| --- | --- |
| [Envelope](protected-envelope.schema.json) | Public format, suite, nonce, ciphertext with authentication tag, opaque recipient slot and wrapped data key. A locked reader can inspect this record without fetching a credential. |
| [Logical manifest](protected-manifest.schema.json) | Sealed core identity, selected core checkpoint, corpus, source versions and their contributors, external credential capability requirements and a signed restriction checkpoint. |
| [Restriction checkpoint](protected-restrictions.schema.json) | A trusted journal signer binds the Soul, journal, epoch, exact core checkpoint, complete logical selection and held immutable versions. Verify using the recipient's externally configured trust record. |
| [Credential status](protected-credential-status.schema.json) | A host-local observation of a capability, with state unknown, missing, locked, available, revoked, unavailable or unsupported. The transmitted manifest can declare a requirement. The host supplies the effective status. |
| [Session grant](protected-grant.schema.json) | A host-local authorization binds a verified peer and session to purpose, Soul, definition, recipient, corpus, period, operations, source versions, per-output limit and expiry. |
| [Disclosure ledger](protected-ledger.schema.json) | Durable local budget and reservation receipts shared by every session in one scope. |
| [Freshness recovery decision](protected-recovery.schema.json) | A locally verified, time-bounded exception records the unknown freshness and identifies the authority, host, Soul, core checkpoint, allowed operations and versions. |

Only the sealed envelope is needed in the transport fixture. Its key wrapping lives outside the reusable definition. Keep plaintext keys, bearer credentials, live grants, remaining balances and host recovery permissions under external custody. A recipient can learn the physical ciphertext length, slot, wrapping format, nonce, object count and filesystem metadata. An active observer may additionally see access timing and frequency. While locked, logical paths, file sizes and counts, lineage, credential requirements and restriction details remain sealed. Report logical integrity unchecked, identity unverified and execution unavailable. Unsealing authenticates the encrypted bytes. Authenticate the core identity independently.

## Content binding and external custody

The host strictly parses the authenticated logical document, validates its schema and applies the core checkpoint path rules. The identity and checkpoint agree on Soul ID, revision profile and definition revision. Compare the identity with the independently expected binding. For each selected source, compute `version = sha256(JCS({path, bytes_hex, parents}))` using the tagged lowercase digest. Source versions and paths are unique. Parent references identify immutable contributing versions in the same selection. A missing contributor, invalid version binding or incomplete lineage prevents use. The checkpoint's selected-life inventory must match the source paths and SHA-256 of the decoded file bytes exactly. Core logical modes are carried in the checkpoint.

The fixture suite uses a 32-byte data key, AES-256-GCM, a 12-byte nonce and a 16-byte tag appended to ciphertext. Plaintext is RFC 8785 JCS of the logical manifest. Additional authenticated data is ASCII `SOUL-PROTECTED-MANIFEST-1` followed by one zero byte. RFC 3394 AES-256 key wrap carries the data key under an external recipient key. Hex is lowercase. The fixture keys are public test inputs. A deployment must supply authenticated external custody, a fresh data key or unique nonce per encryption under that key, and an adopted suite and trust policy.

Before rewrap, authenticate the existing content and match the externally authorized identity, source slot and destination slot. Rewrap the same data key. Only the recipient reference and wrapped key change. The identity, definition, selected life, signed restrictions and content ciphertext stay byte-identical. Recovery uses a previously designated external recipient or backend with specific recovery authorization. An unavailable or revoked capability blocks protected use. A copied envelope cannot establish recovery permission. Rewrapping alone cannot revoke a previously retained key or ciphertext. New encryption and access decisions apply prospectively.

The host broker checks the authenticated OS peer and session capability together. Agent processes receive only authorized outputs. Privileged key custody and operations follow [platform PDR-0091](https://github.com/true-line/agent-bot-platform/blob/main/docs/04-decisions/PDR-0091-host-privileged-custody.md). The limited standalone signing exception has its own operation scope. [Platform PDR-0093](https://github.com/true-line/agent-bot-platform/blob/main/docs/04-decisions/PDR-0093-standalone-hq-secure-enclave-signing.md)

A logical credential requirement names a binding reference, intended principal, purpose, scope and backend capability. Distinguish secret retrieval, scoped token issuance, brokered operations, content unwrapping, status inspection and writes. A destination verifies backend and account identity before reporting that binding available. An unsupported capability, an unresolved binding or a principal mismatch prevents the dependent operation. Protected inference uses a brokered operation that keeps the provider key outside the agent environment. Status inspection exposes only the caller’s authorized metadata. The locked projection can report an unknown capability status without revealing private binding details.

## Policy, accounting and revocation

The host supplies trust anchors, verified grants, revocations, recovery decisions, current time, verified freshness and budget policy independently of package content. Execution, approval of changes, content disclosure, export, rewrap, quarantine and release are distinct operations. The authorization result `allowed` is specific to the requested operation. Host execution readiness, other necessary permissions and successful execution are separate results. Expiry is exclusive, in Unix seconds. Recheck authority, current restrictions and the entire source lineage at each authorization, including cache hits and resumed sessions.

The disclosure ledger key is the tuple `(host, soul_id, recipient, corpus, period)`. Grants for the same principal or recipient group share this ledger across sessions, concurrent requests, token renewals and broker restarts. Limits and period changes require budget authority. This fixture charges actual output bytes for each delivery, including summaries and repeat disclosures. Its selected outputs are complete files. Source references and their ancestry identify what was charged. A host with unavailable lineage, accounting or custody must withhold output. A destination establishes its own authorized local budget.

Authorize and durably reserve in one serialized transaction before any bytes leave the broker. Check an unused receipt ID within the ledger, the per-output limit and the sum of existing reservations plus the proposed output against the ceiling. A repeated ID releases no additional bytes. On an interrupted delivery with uncertain outcome, retain the full reservation. Record the version and grant ID, which resolves to the authenticated session and scope in local history. Never restore the source's grants or ledger as spendable destination state.

A held version blocks use of itself and all transitive derivatives, including export of affected material. The signed journal's snapshot lists direct holds. Separate local holds also apply. An ordinary dream may report a finding. Release requires an independently authorized reviewer, a recorded basis, current applicable policy and rechecking dependent material. Record the local decision and advance the local epoch. Keep the original finding, previous signed snapshot and evidence. A restriction committed before authorization takes effect on that decision. Already authorized or in-flight disclosures remain accounted for. Revocation prevents subsequent authorizations and cannot recall delivered bytes.

## Restore and unknown freshness

The example signs ASCII `SOUL-PROTECTED-RESTRICTIONS-1`, one zero byte and JCS of the exact statement using Ed25519. Bind `checkpoint_sha256` to SHA-256 of JCS of the complete core checkpoint. Bind `selection_sha256` to SHA-256 of JCS of the manifest with its top-level `restrictions` member omitted. This binds paths, bytes, lineage, corpus, identity and credential requirements even when a recipient can re-encrypt the manifest. Match Soul, source installation, restriction epoch, journal identity and signer against that checkpoint and the externally trusted journal key. An authentic historical checkpoint establishes historical content integrity.

Compare epochs only within the same trusted Soul and journal. A receiver retains its authenticated high-water mark for that source journal separately from local holds. A lower imported epoch refuses rollback. Equal epochs with different held sets are a conflict and block protected work. A later authenticated snapshot may advance the source journal. A destination's own restrictions survive restore. A higher epoch by itself cannot establish global freshness.

An offline recipient that cannot establish required freshness may inspect the outer envelope. Protected work waits for fresh authority or a recorded recovery decision. Verify the external recovery authority and decision, exact checkpoint, destination host, Soul, expiry, operation and all contributing versions. A bounded decision can permit the specified disclosure or execution while freshness still reads unknown. The normal grant, accounting, custody and known holds continue to apply. Key recovery and freshness recovery require independent authority.
