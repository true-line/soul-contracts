# Draft: contents-1 definition digest

**Proposal for review; not an accepted contract or authority to admit a Soul.**
This draft resolves byte choices left to WP1 in the [HQ migration plan §5.3](https://github.com/true-line/agent-bot-hq/blob/main/docs/daemon-plugin-split.md#53-digests-and-manifest). It is input to [soul-package #1](https://github.com/true-line/soul-package/issues/1), not an implementation or an amendment to current admission policy. A cross-repository decision must follow the platform decision process before these rules bind consumers. The [package format](https://github.com/true-line/agent-bot-platform/blob/main/docs/03-architecture/interfaces/package-format.md#digests-and-pinning) and the plan identify the Definition class and the manifest's self-reference exclusion; the detailed representation below is a proposed choice.

## Proposed v1 byte rules

1. The package root is the directory containing `Contents/`. A definition consists of the required regular files `Contents/SoulInfo.json` and `Contents/SoulLock.json`, and every regular file recursively under `Contents/primitives/` if present. Other classes, including `host/`, `home/`, `workspaces/`, `opt/`, `comms/`, `cache/` and `tmp/`, are not traversed and do not contribute. Directories are not entries. An absent and an empty `primitives/` have the same digest.
2. A manifest path is relative to `Contents/`, using `/` separators. Each component must be nonempty valid UTF-8 in NFC, and must not be `.`, `..`, contain a backslash, U+0000–U+001F or U+007F. Absolute paths and duplicate paths are invalid. A non-NFC name is refused rather than silently renamed. Selected paths and their ancestors must not be symlinks, and selected leaves must be regular files; refuse other file types. No file or directory entries outside the selected definition are examined for hashing.
3. Hash every selected file's exact bytes with SHA-256, except `SoulLock.json`: parse it as UTF-8 JSON with duplicate object keys and invalid Unicode rejected; require a JSON object; remove its **top-level** `definition_digest` member if present; serialize the remaining object with RFC 8785 JCS and UTF-8 encode it. Nested members with that name remain. The lock projection is used for both its file hash and byte size. This separate exclusion resolves the lock's self-reference; the producer may calculate before the field exists, while an importer must additionally check that a present claimed digest equals the calculated digest. The accepted lock format and other field validation remain separate contracts.
4. For each file, the entry value is exactly `{ "sha256": <64 lowercase hex>, "size": <nonnegative integer>, "mode": <string> }`. `size` is the byte length of the hashed content and must not exceed 9007199254740991. The mode is `100755` if any execute bit is set, otherwise `100644`; ownership, other permission bits, timestamps, extended attributes and ACLs do not contribute. Safety and access-control checks are separate from hashing.
5. Construct the manifest object exactly as `{ "format": "contents-1-definition-v1", "files": { <path>: <entry>, ... } }`. The manifest is an in-memory projection; it has **no digest member**. If a stored or signed representation adds a digest member, that member is not part of this object. Serialize the object as RFC 8785 JCS, encode UTF-8, and compute SHA-256. The result is `sha256:` followed by 64 lowercase hex digits. JCS sorts object keys according to RFC 8785; filesystem enumeration order is irrelevant.
6. Producers and verifiers must apply the same rules to a stable snapshot and fail if selected entries change during the read. Digest equality establishes byte identity under these rules; it does not itself establish provenance, acceptance, permission to execute, or protected-profile qualification.

## Choices requiring maintainer review

- Whether the digest belongs in `SoulLock.json`, a separate manifest, or both, and which fields are excluded from each representation. This proposal excludes only the top-level lock field and constructs a manifest with no digest field; it does not recursively strip names.
- Whether canonicalizing the lock while hashing other files as exact bytes is the desired compatibility rule. This avoids whitespace-dependent self-reference; the choice means lock whitespace and object-key order do not change the digest.
- Whether NFC-only names, refusal of links, executable-bit normalization and omission of empty directories are the desired portability constraints. Filesystem safety and size limits need their own validator contract.
- Whether case-colliding names such as `primitives/Guide.md` and `primitives/guide.md` must be rejected by importers or supported only on a case-sensitive target. The proposed byte rules distinguish them but do not define safe installation on a case-insensitive macOS volume. No portability claim is made for such a package.
- Whether the manifest envelope and version string should be this shape, and whether to require `primitives/` even when empty. Adoption must define rollout/version negotiation and independent implementations before consumers rely on a digest.

`vectors.json` is deliberately separate from the accepted `fixtures/` tree. Its base64 content represents exact input bytes. Positive cases include exact projected lock bytes, full manifest, exact canonical manifest text and digest. The `base` input contains a claimed digest equal to the computed digest. `lock-reformatted-and-claimed-value-changed` deliberately contains a wrong claim: its producer projection has the same computed digest, but an importer must reject the mismatch. The `claimed_digest_matches` field records this comparison for each producer case. Equality is only the digest comparison, not evidence that the whole package passes import validation or has owner acceptance. The negative cases specify rejection boundaries, not new registry error codes. Generic JCS vectors in `fixtures/canonicalization/jcs.json` test the serializer separately; they are not definition-digest vectors.
